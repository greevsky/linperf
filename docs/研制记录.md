# linuxtui 研制记录

这份记录汇总 2026-10-08 这次研制开始前的讨论、调研结论，以及改到 Linux 服务器上开发的原因。后续设计变更也写在这里。

2026-10-09 我把名字定为 linuxtui，没有对应的中文名。下面 10 月 8 日的段落保持当时的叫法和路径，那时候命令还是 linperf。

## 目标

做一款 Linux 综合性能智能分析的单体软件：一个二进制，在一台机器上完成采集、存储、分析、解释和呈现。结论必须能回到指标和证据，而不是只给一张图。

## 第一轮：研制时要考虑的方面

当时整理的范围如下，作为后续设计和取舍的底稿。

1. 产品边界。使用者是管理员、SRE、应用开发和内核排查人员。第一版看单机，包括这台机器上的容器和 cgroup，不做成多机观测平台。「综合」覆盖硬件与 NUMA、CPU 调度、内存、块设备和文件系统、网络、运行时、进程与容器。「智能」的交付物是异常、关联、可能原因、下一步证据和可导出的报告。
2. 采集面。常驻计数来自 `/proc`、`/sys`、cgroup、PSI、netlink。硬件看 PMU、RAPL、温度、NUMA、中断。动态追踪看 `perf_event`、tracepoint、kprobe、eBPF。权限分级：无特权只读 `/proc`；`CAP_PERFMON` / `CAP_BPF` 打开动态追踪。启动时做特性探测，按内核能力选择路径。容器要处理 PID、mount、net、cgroup namespace。
3. 指标体系。资源用利用率、饱和度、错误。服务看速率、错误、延迟。压力看 PSI。关联键至少有时间、CPU、PID、cgroup、设备、网卡、NUMA、容器 ID。每个指标要写清单位、累计还是瞬时、采样间隔，以及在容器和虚拟机里会不会失真。
4. 智能分析。先做确定性规则，再做统计，再把证据链挂在结论旁边。语言模型只负责把已有证据写成说明，不直接裁决根因。指标缺失或计数器不可信时，输出数据不足。
5. 单体架构。一个可执行文件，内部分采集、存储、分析、界面、导出。eBPF 字节码内嵌，不把 BCC、Python、LLVM 运行时变成目标机器上的硬依赖。界面要有 TUI、本地 Web 或 CLI 里本次选定的几种，并且读同一份结果。动态追踪放在可失败、可降级的路径上，计数采集继续可用。
6. 自身开销。默认只开低开销计数。火焰图、off-CPU、syscall 追踪由用户显式打开，并说明预计开销。
7. 本地存储。热数据在内存环形缓冲，诊断结果可以导出成快照。不把远程时序库当成必需组件。
8. 兼容与打包。单二进制覆盖主流发行版。启动自检内核版本、BTF、`perf_event_paranoid`、SELinux/AppArmor、是否在容器里、PMU 是否可用。x86_64 先落地，aarch64 后续要能走同一套探测。
9. 安全与隐私。命令行参数、环境变量、用户数据默认不进长期存储。本地界面不对外网裸奔。
10. 正确性。用录好的 `/proc` 文本做回放测试。关键口径和常见工具对齐。规则用故障样本做回归。
11. 建议顺序。先低开销计数、环形存储和 TUI，把 USE 和 PSI 做完整。再做确定性规则和证据链。然后是诊断快照。eBPF 栈采样和 off-CPU 放进第一版能力，但在内核不支持时自动退回。

## 第二轮：调研结论

| 项 | 选择 |
| --- | --- |
| 问题范围 | 都要，按顺序做：先快速定位和证据，再持续观测和深度追踪 |
| 运行环境 | 以后跑在各种 Linux 发行版上，启动时自动判断能力。当时的开发机是这台 Windows |
| 第一版用法 | 终端界面为主，命令行导出为辅 |
| 分析深度 | 第一版就包含 eBPF 火焰图和 off-CPU |
| 实现 | Rust 单二进制 |
| 文案 | 中文界面，指标名保持英文 |
| 本地目录 | `C:\Users\mr_ch\Projects\linperf` |

两条选择要同时成立：产品按「先定位、再观测、再深挖」的顺序交付；代码结构从第一天就包含 eBPF。内核没有 BTF、没有权限或没有把字节码编进二进制时，自动退到 `/proc` 计数和规则，不能整程序不可用。

## 第三轮：改到远程 Linux 上开发

Windows 开发机会拉长周期，依据是这台机器上的实际情况：

- 没有 Rust 工具链
- 没有 WSL
- 装 Rust 的一次尝试被中断
- eBPF 字节码不能在 Windows 上可靠地编译和加载

## 第一版实现切片

1. `linperf check`：探测 procfs、PSI、cgroup v2、BTF、perf_event_paranoid、CAP_BPF、CAP_PERFMON、CAP_SYS_ADMIN，并用中文写出当前能走哪条采集路径。
2. `linperf snapshot`：间隔采样两次，计算速率，跑确定性规则，输出中文结论。`--json` 导出。`--demo` 用内置的磁盘饱和样本，方便没有负载时看结论长什么样。
3. `linperf watch`：TUI。实时刷新 CPU、内存、IO、网络和结论。`q` 退出，`j` / `k` 选择结论。
4. `linperf export`：把同一次快照写成 JSON。
5. `linperf flame`：把 folded stacks 画成 SVG。`--demo` 不依赖内核。
6. `linperf profile`：在具备条件时加载 eBPF，采 on-CPU 或 off-CPU，写出 folded stacks。不具备条件时说明原因。

规则第一批：`cpu.saturated`、`cpu.iowait`、`cpu.steal`、`memory.pressure`、`memory.swap`、`io.saturated`、`net.drops`、`cgroup.cpu_throttle`、`cgroup.memory_high`。没有命中时给出 `host.healthy`。

eBPF 约定：on-CPU 用 `perf_event` 采样；off-CPU 用 `sched_switch`，在任务离开 CPU 时用 `bpf_get_task_stack` 记下内核栈，等它被再次调度时累计时间。符号优先用 `/proc/kallsyms`。用户态符号后面再补。

## 第四轮：目的、兼容、界面

2026-10-08 把产品目的收成三件事，优先级按这个顺序：

1. 兼容。同一份二进制要能在主流发行版上跑起来。适配的是内核接口，不是某个发行版的软件包。`/proc`、`/sys`、cgroup v1、cgroup v2、混合层级、PSI 有就用，没有就降级，并在 `check` 里说明。发行版识别读 `/etc/os-release`，没有时再看 redhat-release、alpine-release、debian_version。内存在没有 `MemAvailable` 的旧内核上用 MemFree + Buffers + Cached 近似，并在证据里标明。虚拟化从 DMI 和 hypervisor 标志识别，避免把 steal 当成客人机里的热点。
2. 界面。第一眼是当前瓶颈：严重程度、一句判断、证据、下一步。结论按严重程度排列；同一级别里先放占用资源的结论（例如磁盘饱和），再放它引起的等待（例如 iowait）。`j` / `k` 切换时上面的定位区跟着变。四根仪表方向一致，高表示压力，只高亮和当前结论相关的那一根，其余压暗。终端矮或窄时只保留定位和结论列表。
3. 目的。快速定位性能瓶颈，服务问题排查。智能分析在这一版是确定性规则：每条结论带指标、单位和下一份该看的证据。数据不够时说明缺什么，不补一个看起来完整的根因。

快照 JSON 的 `version` 从 1 改为 2，因为主机能力里增加了发行版标识、cgroup 层级和虚拟化。

## 改名

2026-10-09。linperf 这个名字把工具锁在性能上。我现在打开它，先看到的是导航：硬件、进程、容器、防火墙、网络、日志。等保基线、抓包、吞吐和火焰图都在同一个二进制里。性能定位还在，只是其中一块。

名字是 linuxtui。界面、命令和报告抬头都写这个，不另起中文名。

作者跟仓库一致：lei <mr.greevsky@gmail.com>，仓库 https://github.com/greevsky/linperf 。工具里的版权行也是这一条。GitHub 上的仓库名仍是 linperf，工具里的地址用这个仓库。eBPF 字节码仍按内核要求标 GPL，那是加载条件，不是另一套作者信息。
